## 第 0 章 · 为什么要移植到 PX4

我们自己在 Gazebo 里做的仿真已经能跑能飞了，但**缺一块关键的东西：姿态控制器**。

自己写的仿真里，桨一开机器人就会翻 —— 因为没有闭环控制。要自己从零写一个能稳定悬停的姿态控制器（PID + 控制分配 + 传感器融合）工作量巨大，而且很难做得像 PX4 那样成熟可靠。

**PX4 正好提供了这一整套：**

| 能力 | 说明 |
|---|---|
| 传感器融合（EKF2） | IMU + 磁力计 + 气压计 → 姿态/位置/速度估计 |
| 姿态控制 | 串级 PID（角度环 + 角速度环） |
| 控制分配 | 自动把姿态指令翻译成 4 个电机的转速 |
| 位置/高度控制 | 悬停、航点、自动起降 |
| 地面站生态 | QGroundControl、MAVLink 协议 |

所以策略是：**把我们的机器人"接"进 PX4，让它当飞控大脑，我们只负责机体和机构。**

## 第 1 章 · 移植到底难在哪（先建立正确预期）

### 1.1 难点不在"写代码"，而在"对上暗号"

PX4 加载一个仿真模型时，**很多东西是写死在源码里的**，你能改的只有模型文件和参数。这形成了一份**隐式契约**：

```
PX4 说："我只会去订阅这个固定名字的话题，你给我别的名字我就当没看见。"
```

这份契约包括：

| 契约项 | PX4 的硬性要求 |
|---|---|
| 根 link 名 | 必须叫 `base_link`（不能叫 `base`） |
| 舵机关节名 | 必须叫 `servo_0` ~ `servo_7`（不能叫 `joint1`） |
| IMU 传感器名 | 必须叫 `imu_sensor`，且挂在 `base_link` 上 |
| 磁力计名 | 必须叫 `magnetometer_sensor` |
| 传感器话题路径 | **绝对不能自定义 `<topic>`**，PX4 按默认路径找 |
| 电机话题 | `/<实例名>/command/motor_speed` |
| 实例名规则 | `${PX4_SIM_MODEL}` 去掉 `gz_` 前缀，再拼 `_0` |

> **一句话**：移植 = 把我们的 URDF **改名、改话题、加传感器、重定标**，让它长得像 PX4 认识的模型。

### 1.2 还有一份更隐蔽的契约

上面那些是"名字"层面的。**还有一层是"内容"层面的** —— 这条坑了我们最久（见第 3 章）：

```
PX4 订阅了话题，但如果话题里的数据格式不完整，
它会认为"传感器坏了"，而不是"数据不全"。
```

## 第 2 章 · 实施过程

### 2.1 做了一把"自动化锤子"

手工改 URDF 效率低且容易出错，所以写了 **`build_px4_model.py`** —— 一键完成所有改造并自检：

```
robot.urdf  ──[build_px4_model.py]──►  Tools/simulation/gz/models/airground/
                                        ├── model.sdf
                                        ├── model.config
                                        └── meshes/
                                    ──►  ROMFS/.../airframes/4030_gz_airground
```

**它做了 8 件事：**

| # | 改造 | 原因 |
|---|---|---|
| 1 | 根 link `base` → `base_link` | PX4 源码硬编码 |
| 2 | 舵机关节 `joint1/2` → `servo_0/1` | 同上 |
| 3 | 舵机控制话题 → `/model/airground_0/servo_N` | 契约 |
| 4 | 电机插件改成 x500 写法（去掉 `robotNamespace`） | 否则话题路径会错 |
| 5 | 电机参数**重定标** | 见下表 |
| 6 | mesh 路径 → `model://airground/meshes/` | 相对资源路径 |
| 7 | `base_link` 注入 IMU / 磁力计 / 气压计 | 契约 |
| 8 | 生成 airframe 文件并登记到 `CMakeLists.txt` | 否则不被打进 ROMFS |

**电机重定标对照**（PX4 的输出直接当 rad/s 用，不做缩放）：

| 参数 | 自研仿真 | PX4 版 | 说明 |
|---|---|---|---|
| `maxRotVelocity` | 3400 | **1000** | 对齐 x500 量纲 |
| `motorConstant` | 4.325e-7 | **5.0e-6** | 由 TWR=3 反推 |
| `momentConstant` | 2.163e-8 | **2.5e-7** | KT × 0.05 |
| `rotorVelocitySlowdownSim` | 10 | 10 | 不变 |

### 2.2 机架文件里最关键的一条

```bash
# ROMFS/px4fmu_common/init.d-posix/airframes/4030_gz_airground

# 悬停油门 —— 不设这条飞机根本抬不起来！
param set-default MPC_THR_HOVER 0.5774
```

**为什么？** PX4 默认以为 50% 油门就该悬停（对应推重比 2 的机型）。我们的推重比是 **3.0**，理论悬停油门是：

$$\text{MPC\_THR\_HOVER} = \frac{1}{\sqrt{\text{推重比}}} = \frac{1}{\sqrt{3}} = 0.5774$$

**不设的话，起飞油门爬到 575 就卡住不动了**，飞机纹丝不动 —— 这个现象很有迷惑性，看起来像"推力不够"，实际是"油门到顶了"。

### 2.3 登记到清单（容易漏）

`airframes/CMakeLists.txt` 是**显式列名**的清单，不是通配符：

```diff
        4021_gz_x500_flow
+       4030_gz_airground
```

**不登记的话 `make` 不会把机架文件打进 ROMFS**，PX4 启动时找不到机型。

## 第 3 章 · 坑一：STALE 导致无法解锁

### 症状

- PX4 日志里反复出现 `STALE` 警告，涉及 Gyro / Accel / BARO / MAG
- 发解锁命令 → 返回 **`TEMP_REJECTED`**（暂时拒绝）
- 电机指令恒为 `[0,0,0,0]`

### 排查走过的弯路

| 试过的假设 | 结果 |
|---|---|
| spawn 高度太低？改 z=0.05 | ❌ STALE 从 7 次降到 3 次，没根治 |
| 仿真太慢？ | ❌ 实测 RTF = 1.0，正常 |
| 话题名不匹配？ | ❌ `gz topic -i` 确认 PX4 的订阅者就在列表里 |
| airframe 参数没生效？ | ❌ 读参数确认 `CA_ROTOR_COUNT=4` 等全对 |
| 传感器写了 `<topic>`？ | ⚠️ 这确实是个真 Bug，但修了之后**仍然 STALE** |

### 真正的根因

**传感器块必须写完整的配置子元素。**

```xml
<!-- ❌ 错的写法：只写名字和频率 -->
<sensor name="imu_sensor" type="imu">
  <always_on>1</always_on>
  <update_rate>250</update_rate>
</sensor>
```

```xml
<!-- ✅ 对的写法：必须补上完整的配置子元素 -->
<sensor name="imu_sensor" type="imu">
  <always_on>1</always_on>
  <update_rate>250</update_rate>
  <imu>
    <angular_velocity>
      <x><noise type="gaussian"><mean>0.0</mean><stddev>0.0008726646</stddev></noise></x>
      <y><noise type="gaussian"><mean>0.0</mean><stddev>0.0008726646</stddev></noise></y>
      <z><noise type="gaussian"><mean>0.0</mean><stddev>0.0008726646</stddev></noise></z>
    </angular_velocity>
    <linear_acceleration>
      <x><noise type="gaussian"><mean>0.0</mean><stddev>0.00637</stddev></noise></x>
      <!-- y / z 同理 -->
    </linear_acceleration>
  </imu>
</sensor>
```

磁力计要补 `<magnetometer>`（x/y/z 各一个噪声块），气压计要补 `<air_pressure>`（pressure 噪声）。

**最省事的做法：直接照抄 `Tools/simulation/gz/models/x500_base/model.sdf`。**

### 结果

| 指标 | 修前 | 修后 |
|---|---|---|
| STALE 出现次数 | 4 次 | **0 次** |
| 解锁结果 | `TEMP_REJECTED` | **`ACCEPTED`** |
| 电机指令 | `[0,0,0,0]` | **`[0.7, 1.3, 0.7, 1.4]`** |

### 教训

> **PX4 的模型接口是"隐式契约"—— 名字对、话题对还不够，传感器内部的配置块也必须完整。**
> 少一个 `<imu>` 子元素，整条链路就瘫掉，而 PX4 给的提示是"传感器坏"，非常有误导性。

## 第 4 章 · 坑二：起飞就翻覆（最凶险的一个）

### 症状

解锁正常了，推力也够了（`MPC_THR_HOVER` 修好后能爬升到 10 cm），但：

```
   t      z(m)    roll     pitch     PX4 电机指令
 2.9s   +0.027    +0.1°    -1.6°    [604, 607, 582, 585]   ← 一切正常
 3.1s   +0.058    +2.7°    -3.6°    [588, 665, 569, 646]   ← 开始歪
 3.3s   +0.151   +61.6°    -3.1°    [199, 988,  10, 847]   ← 0.2 秒内炸到 61.6°！
 3.5s   +0.182   -67.1°    +0.1°    [  0, 979,  10, 990]
 4.1s   +0.255  -168.5°    -2.3°    [  0, 604, 348, 952]   ← 翻了
```

**离地之后 0.2 秒内横滚角速度冲到 481°/s，然后翻成肚皮朝天，卡死不动。**

### 排查过程（9 个环节逐个排除）

| # | 假设 | 怎么验证 | 结论 |
|---|---|---|---|
| 1 | 摆臂舵机被推力扭动？ | 读 `servo_0/1` 关节角 | ❌ 全程 **−0.00°**，纹丝不动 |
| 2 | `CA_ROTORx_KM` 偏航符号错？ | 读 model.sdf 的关节轴 ±Z 后重算 | ❌ 原值正确 |
| 3 | 桨超高速空转产生陀螺效应？ | 同时读关节位置和速度 | ❌ 那个 15551 是我把**累积位置**读成了速度 |
| 4 | `rotorVelocitySlowdownSim` 缺失？ | grep 模型文件 | ❌ 其实在（grep 输出被换行截断误导了我） |
| 5 | 桨位置数值算错？ | 写前向运动学脚本核对 | ❌ 与真实重心**完全吻合** |
| 6 | PX4 姿态估计不准？ | 对比 PX4 估计 vs Gazebo 真值 | ❌ 差 **<0.1°** |
| 7 | 碰撞体插进地面？ | 算所有碰撞体的最小 z | ❌ 4 轮刚好贴地，其余离地 1.8~7.6 cm |
| 8 | 增益过高？ | 降 3 倍重测 | ❌ **症状一模一样** |
| 9 | **坐标系左右镜像？** | 读出 airframe 里的 PY 符号 | ✅ **就是它** |

> ⚠️ 第 8 项特别值得记：我降了增益后症状完全一样，这**排除了"控制器调参"方向**，把注意力推回到了"物理/几何"上。

### 真正的根因：坐标系手性搞反了

```
URDF / Gazebo（REP-103 标准）： x 前、y 左  、z 上
PX4（NED / FRD）             ： x 前、y 右  、z 下
```

关键的一步是这样的：

```
joint3 在 URDF 里的位置是 y = −0.1100
```

- 按 **Gazebo** 的约定：`y = −0.11` 是**右侧** ✅
- 而 airframe 里写的是 `CA_ROTOR0_PY −0.1100`
- **PX4 按自己的约定理解成"左侧"** ❌

→ **整个左右布局被镜像了** → **横滚控制环变成正反馈**（越纠越歪）→ 一离地就炸。

### 为什么偏偏是横滚出问题、俯仰正常？

因为 **x 轴在两套坐标系里是同向的**（都是"前"），只有 **y 轴反向**。所以：

| 轴 | 是否受影响 | 观察到的现象 |
|---|---|---|
| 俯仰（pitch） | 不受影响 | ✅ 数据里俯仰一直很正常 |
| **横滚（roll）** | **反向** | ❌ 一离地就发散 |
| 偏航（yaw） | 反向 | ❌ 出现过 `[0,0,1000,1000]` 这种怪的偏航指令 |

### 修法

```python
# build_px4_model.py
pos = [(0.1008, +0.1100), (0.1008, -0.1100),
       (-0.1092, +0.1100), (-0.1092, -0.1100)]
#              ^^^^^^^ 把 URDF 的 y 取反
```

**KM 符号不用动**（由桨的真实旋转方向决定，与 y 取反无关）。

### 一个"改对了"的自检判据

改完后，**`KM` 同号的桨应该落在对角线上** —— 这正是 PX4 官方 quad-X 的标准布局：

```
            桨1 (KM −0.05)        桨0 (KM +0.05)
                  \                 /
                   \   机身(俯视)   /
                    \             /
            桨2 (KM −0.05)        桨3 (KM +0.05)
```

**如果 KM 同号的桨没落在对角线上，八成是左右或前后轴搞反了。**

### 效果对比

| 指标 | 修改前 | 修改后 |
|---|---|---|
| 起飞 | 3 秒内翻覆 | **平稳爬升** ✅ |
| 悬停高度 | 0.084 m（躺在地上） | **2.0 ~ 2.55 m** ✅ |
| 横滚 | ±180° | **±0.3°** ✅ |
| 俯仰 | ±85° | **±0.2°** ✅ |
| 悬停时长 | 0 | **>27 秒不翻** ✅ |

### 教训

> **跨仿真器移植时，"坐标系手性差异"是最隐蔽的坑。**
>
> **症状特征**：某一个轴的控制变成正反馈，其他轴正常。
> 看到这个特征，第一反应就该去查那个轴的坐标约定。
>
> **自检判据**：KM 同号的桨应落在对角线上。

## 第 5 章 · 坑三：悬停慢晃（自己给自己下的套）

### 症状

飞机能飞了，悬停 27 秒也不翻，但有毛病：

```
     t      z      | 真 roll pitch  yaw | PX4 电机指令
    0.0s +1.840   |   -0.0  -0.2   -9.0 | [800, 228, 159, 783]
   11.5s +1.605   |   -0.2  +0.2  -36.9 | [583, 593, 570, 560]
   21.5s +1.740   |   -0.0  +0.1  -21.0 | [383, 738, 720, 347]
```

- **偏航缓慢摆动了 17°**
- 水平位置漂移了 **1.1 米**
- 电机差动极大（`[800,228,159,783]` 这种）

### 排查方向一度被带偏

我一开始以为是传感器问题，查了好几轮磁力计（见第 6 章）。

### 真正的根因：我自己改的参数被持久化了

事情是这样的：

1. **第 23 窗口**：为了验证"增益过高导致翻覆"的假设，我在运行时把速率环增益砍了一半：
   ```
   MC_ROLLRATE_P:  0.15 → 0.05
   MC_ROLL_P:      6.5  → 3.0
   MC_YAWRATE_P:   0.2  → 0.1
   ```
2. **第 25 窗口**：那个假设**被证伪了**（真因是左右镜像，跟增益无关）。但我**忘了把参数恢复**。
3. **PX4 SITL 会把运行时改的参数持久化到 `build/px4_sitl_default/rootfs/parameters.bson`** —— 跨进程保留。
4. 于是后面所有实验都在带着这些**被砍过的增益**跑 → 悬停慢晃。

### 恢复出厂后

| 指标 | 砍过增益时 | 恢复出厂后 |
|---|---|---|
| 高度波动 | ±0.09 m | **±0.04 m** |
| 水平漂移 | 1.1 m | **< 7 cm** |
| 横滚 | ±14° | **±0.3°** |
| 俯仰 | ±13° | **±0.2°** |
| 偏航变化 | 17° | **0.3°** |
| 电机离散度 | 0 ~ 800 | **545 ~ 606** |

**提升了一个数量级。**

### 附带发现：我"恢复出厂"时恢复错了

我一度以为出厂增益是 `MC_ROLL_P/PITCH_P = 6.5`，于是"恢复出厂"时**填成了 6.5**。

后来做 A/B 对照才发现：**这个 PX4 版本的出厂值其实是 `4.0 / 4.0 / 2.8`**。

> ⚠️ **不同 PX4 版本的默认增益会变，必须实测，不能凭记忆。**

### 怎么精确查出"哪些参数被改过"

`parameters.bson` **只存非默认值**（出厂时只有 312 字节）。所以：

```bash
# 1. 把参数文件挪走
mv build/px4_sitl_default/rootfs/parameters.bson /tmp/
mv build/px4_sitl_default/rootfs/parameters_backup.bson /tmp/

# 2. 启动一次 PX4（生成纯出厂版）
make px4_sitl gz_airground

# 3. 抓出里面的参数名
strings build/px4_sitl_default/rootfs/parameters.bson | grep -E '^[A-Z][A-Z0-9_]{3,}$'

# 4. 和原来的对比，差异就是被改过的参数
```

用这个方法精确锁定了：**只有 3 个参数被改过**（`MC_ROLL_P` / `MC_PITCH_P` / `MC_YAW_P`）。

### 效果：真·出厂增益反而更好

```
              真出厂(4.0/4.0/2.8)   之前用的(6.5/6.5/2.5)
z 幅度            0.055 m              0.040 m
x 幅度            0.060 m             ~0.070 m
roll 幅度         0.571°               0.700°   ← 更好
pitch 幅度        0.464°               0.480°
```

**结论：根本不需要调增益，用出厂值就够。**

### 教训

> 1. **PX4 SITL 的 `param set` 会持久化**，跨进程保留。做 A/B 实验改完参数**必须显式恢复**，否则会污染后续所有实验。
> 2. **别凭记忆认定"出厂值"** —— 换版本就可能变，要用"挪走 bson 重启"的方法实测。
> 3. 调试时最好**一次只改一个变量**，并记录改了什么。

## 第 6 章 · 两个"以为是 Bug，其实不是"的误判

### 误判 ①：磁力计镜像

**怀疑的起因**：悬停时发现 **PX4 的航向在"倒着转"**：

| 时间段 | 真实航向变化 | PX4 估计变化 |
|---|---|---|
| 0 → 3.5s | **−3.5°** | **+3.4°** |
| 3.5 → 7.5s | **−3.5°** | **+3.1°** |
| 11.5 → 15.5s | **+1.5°** | **−1.2°** |

看起来完美镜像。加上 PX4 源码里那段注释：

```cpp
// FIXME: once we're on jetty or later
// The magnetometer plugin publishes in units of gauss and in a weird left handed coordinate system
_px4_mag.update(timestamp, -msg.field_tesla().y(), -msg.field_tesla().x(), msg.field_tesla().z());
```

**看起来像是 PX4 的坐标变换补丁和我们的 gz 版本对不上。**

**怎么推翻的**：拿**官方模型 gz_x500 做同样的实验**：

| 真实偏航(ENU) | 官方 gz_x500 | 我们 airground | 差异 |
|---|---|---|---|
| 0° | +92.56° | +92.58° | **0.02°** |
| 45° | +47.71° | +47.56° | **0.15°** |
| 90° | +2.57° | +2.60° | **0.03°** |
| 180° | −87.44° | −87.51° | **0.07°** |
| 315° | +137.56° | +137.56° | **0.00°** |

**两者逐位一致** → **我们的磁力计链路和官方模型完全相同，没有 Bug。**

**那"倒着转"是怎么回事？** 是 **ENU 和 NED 坐标系转换的数学必然**：

$$\text{ENU}: (x,y,z)=(东,北,天) \qquad \text{NED}: (x,y,z)=(北,东,地)$$

$$\text{ENU}\to\text{NED}=\begin{pmatrix}0&1&0\\1&0&0\\0&0&-1\end{pmatrix}, \qquad \det=-1$$

**行列式 = −1 → 这是"镜像变换"不是旋转** → 同一个物理旋转，在两套坐标系里看**方向必然相反**。

$$\boxed{\text{PX4 航向} = \text{常量} - \text{Gazebo 航向}}$$

那 96° 的"偏差"也是同一回事 —— 其实就是 ENU 磁偏角换算到 NED 后的值，**x500 也是 95.9°**。

**结论：磁力计没有 Bug，不需要修。**

### 误判 ②：摆臂被推力扭动

**怀疑的起因**：起飞翻覆时，我算了一下推力对摆臂产生的力矩：

```
单个桨推力 ~1.7 N，相对摆臂轴的偏移 0.0825 m
→ 单桨力矩 = 0.14 N·m
→ 一侧两桨叠加 = 0.28 N·m
```

**看起来足以扭动摆臂**，让推力矢量倾斜 → 翻覆。

**怎么推翻的**：直接在起飞过程中读 `servo_0` / `servo_1` 的关节角：

```
   t      z(m)   servo_0   servo_1
  1.0s  +0.021    -0.00     -0.00
  3.5s  +0.222    -0.00     -0.00
  4.1s  +0.269    -0.00     -0.00
  8.0s  +0.086    -0.00     -0.00
```

**全程纹丝不动（−0.00°）** —— 0.28 N·m 被 0.7 N·m 的舵机稳稳扛住了。

**结论：不是这个原因。（也顺便验证了舵机选型是对的。）**

## 第 7 章 · 附带查清的几件事

### 7.1 `MAV_CMD_DO_SET_MODE` 的参数格式（我踩了）

写脚本切飞行模式时一直失败，返回 `TEMPORARILY_REJECTED`。查接收端源码才发现：

```cpp
// Commander.cpp:922
case vehicle_command_s::VEHICLE_CMD_DO_SET_MODE: {
    uint8_t base_mode        = (uint8_t)cmd.param1;   // 要含 CUSTOM_MODE_ENABLED 位
    uint8_t custom_main_mode = (uint8_t)cmd.param2;   // ← 主模式直接填！
    uint8_t custom_sub_mode  = (uint8_t)cmd.param3;   // ← 子模式
```

**参数是"拆开的"，不是打包值：**

```python
# ❌ 我一开始这么写的（想切 POSCTL）
param2 = 3 << 16 = 196608     # → & 0xFF = 0 → 无效主模式 → 被拒

# ✅ 正确写法
param1 = 1        # MAV_MODE_FLAG_CUSTOM_MODE_ENABLED
param2 = 3        # 主模式：POSCTL
param3 = 0        # 子模式
```

> ⚠️ **注意区分**：**HEARTBEAT 里的 `custom_mode` 是打包格式**（main 在 bits 16-23），
> 和 `DO_SET_MODE` 的**入参格式不一样**。两者容易混淆。

### 7.2 `vehicle_command_ack lost` 是什么意思

PX4 控制台偶尔刷这个：

```
ERROR [mavlink] vehicle_command_ack lost, generation 6 -> 13
ERROR [mavlink] vehicle_command_ack lost, generation 6 -> 13    ← 同一行重复好几遍
```

源码在 `mavlink_main.cpp:3007`：

```cpp
while ((get_free_tx_buf() >= COMMAND_ACK_TOTAL_LEN) && _vehicle_command_ack_sub.updated()) {
    if (_vehicle_command_ack_sub.get_last_generation() != last_generation + 1) {
        PX4_ERR("vehicle_command_ack lost, generation %u -> %u", ...);
```

**翻译**：
> "遥测把发送缓冲区占满了，命令回执通知我漏发了几条。"

**触发条件（已实测复现）**：QGC 刚连接时会批量请求几十种高频数据流 → 发送缓冲区占满。

| 实验 | 结果 |
|---|---|
| 只连发 180 条命令，不请求数据流 | **0 次**报错 |
| 先请求 32 种消息 × 高频，再发命令 | **4 次**报错 ✅ 复现 |

**为什么同一行重复 3~4 次？** 因为 PX4 同时开着 **4 条 MAVLink 链路**：

```
18570  GCS（给 QGC）
14580  offboard
14280  onboard payload（相机）
13030  onboard gimbal（云台）
```

每条链路各自检查缓冲区，都被占满 → 同一错误报 4 遍。

**要不要管？不用。** 命令照常执行、仿真不受影响；只是个别 `COMMAND_ACK` 可能没到 QGC，QGC 偶尔显示"命令超时"并自动重试。**换成官方 x500 也一样。**

### 7.3 PX4 与 QGC 的连接

PX4 启动时会打这条日志：

```
INFO  [mavlink] mode: Normal, data rate: 4000000 B/s on udp port 18570 remote port 14550
```

**它自己会往 14550 发** —— 那正是 QGC 的默认监听端口，所以 **QGC 开箱自动连上，不用手动配**。

（端口定义在 `ROMFS/px4fmu_common/init.d-posix/px4-rc.mavlink`）

### 7.4 顺带修好的一个真 Bug：触地联锁

`air_ground_ctrl.py` 里用 `/world/default/contact` 话题判断是否触地。实测这个**话题根本不发布**（订阅成功、9 秒 0 条消息），尽管世界文件里声明了 Contact 插件。

**后果**：`on_ground` 永远是 `False` → **任何超过 48° 的指令都被立刻拽回 0°** → 地面模式完全没法用。

**修法**：改用**机身高度**判断。

**但这里又踩了第二个坑** —— 实测发现 **折叠摆臂本身就会把机身撑高**：

```
摆臂  0°  → 机身 z = 0.0210 m
摆臂 26°  → 机身 z = 0.0624 m
摆臂 52°  → 机身 z = 0.1014 m      ← 地面上机构全行程的最大高度
```

第一版阈值设成 0.08 m，结果**摆臂转到 33° 就超过阈值 → 被判"空中" → 拽回 0° → 高度降回 → 又被允许** → 死循环。

**最终取 `ON_GROUND_Z = 0.20`（机构最大高度的 2 倍）**，问题解决。

> ⚠️ **教训**：用某个状态量做判据前，**先确认它不会被被控对象本身改变**。
> 这里"机身高度"会被"摆臂角度"改变，形成了反馈环。
> 判据要么选与被控量解耦的量，要么**阈值取到超出机构行程**。

## 第 9 章 · 经验提炼

### 🥇 经验一：跨仿真器移植，"坐标系手性差异"是最隐蔽的坑

- **症状特征**：某一个轴的控制变成正反馈，其他轴正常
- **自检判据**：`KM` 同号的桨应落在**对角线**上
- **终极判据**：拿**官方参考模型（x500）做同样的实验对照**，一比就知道

### 🥈 经验二：能用实测回答的问题，绝不用推理回答

这一轮里，**三次**靠实测推翻了自己的推理：

| 推理 | 实测结果 |
|---|---|
| "磁力计补丁和 gz 版本对不上" | ❌ x500 一模一样 → 没有 Bug |
| "出厂增益是 6.5" | ❌ 这版是 4.0 |
| "`DO_SET_MODE` 参数是打包值" | ❌ 是拆开的 |

**三个特别有用的实测手法：**

1. **挪走参数文件重启** → 拿到真正的出厂基线
2. **拿官方模型跑同样实验** → 判断"是我的问题还是通病"
3. **读源码代替猜** → 尤其 `grep` 报错字符串，定位到具体代码行

### 🥉 经验三：用状态量做判据前，先确认它不会被被控对象改变

触地联锁用"机身高度"，而"摆臂角度"又会改变机身高度 → 死循环。
**判据要么选与被控量解耦的量，要么阈值取到超出机构行程。**

### 其他值得记住的点

| 经验 | 说明 |
|---|---|
| **一次只改一个变量，并记录** | PX4 SITL 参数会持久化，改完必须显式恢复 |
| **报错的提示可能非常有误导性** | "传感器坏（STALE）"其实是配置块不完整 |
| **对照实验价值极高** | 花 2 分钟跑一次 x500，省下几小时瞎猜 |
| **读参数别快速连发请求** | PX4 会丢包（实测 29 个请求只回了 11 个），要看全量就用 bson 对比法 |
